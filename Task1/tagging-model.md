# Механизм тегирования данных

## Цели

Теги нужны, чтобы чувствительные данные можно было находить, защищать, передавать только по разрешённым потокам, отслеживать в Data Lineage и проверять при релизах новых систем.

Модель покрывает:

- классификацию данных по чувствительности;
- связь данных с владельцем, источником и целью обработки;
- правила доступа RBAC/ABAC;
- автоматическое применение защиты: шифрование, маскирование, токенизация, обезличивание;
- аудит доступа и алерты по нетипичным действиям;
- удаление, архивирование и прекращение обработки по запросу субъекта данных.

## Базовые теги

| Тег | Значение | Примеры данных | Базовое правило |
|---|---|---|---|
| `PII` | Персональные данные | ФИО, дата рождения, телефон, email, адрес | Доступ только по роли и цели обработки |
| `PHI` | Медицинская информация | Диагноз, хронические заболевания, медкарта, анализы | Доступ медролям и пациенту к своим данным; полный аудит |
| `FIN` | Финансовые данные | Платёж, чек, сумма услуги, бухгалтерские документы | Доступ кассе и бухгалтерии, без медицинских деталей |
| `HR` | Данные сотрудников | Зарплата, кадровый учёт, налоги | Доступ бухгалтерии и уполномоченным руководителям |
| `OPS` | Операционные данные | ТМЦ, закупки, поставщики, складские документы | Доступ складу, бухгалтерии и ответственным за закупки |
| `ANALYTICS` | Аналитические наборы | BI-отчёты, P&L, ABC-анализ, ML/AI-датасеты | Использовать только с `PROCESSED` или `ANONYMIZED`, если есть риск PII/PHI |
| `SECRETS/KEYS` | Секреты и ключевые материалы | Ключи шифрования, сертификаты, API-токены, сервисные пароли | Хранить отдельно от данных, выдавать по минимальным правам, журналировать использование |
| `CONFIDENTIAL` | Конфиденциальные внутренние данные | Договоры, поставщики, закупки | Запрет публичного распространения, доступ по роли |
| `PUBLIC` | Публичные данные | Расписание филиала без персональных данных | Можно использовать без специальных ограничений |
| `RAW` | Сырые данные | Сканы, первичные Excel-журналы, необработанные выгрузки | Хранить ограниченно, не передавать в аналитику без обработки |
| `PROCESSED` | Обработанные данные | Проверенные записи, нормализованные справочники | Сохранять Data Lineage и контроль качества |
| `GOLDEN_SOURCE` | Источник правды | Единая запись пациента, договор, платёж | Строгий контроль изменений и владельца данных |
| `ANONYMIZED` | Обезличенные данные | BI/ML/AI датасеты без прямой идентификации | Допустимы для аналитики при проверке невозможности реидентификации |
| `RETENTION_REQUIRED` | Данные с обязательным сроком хранения | Медкарта, договор, согласие, чек | Нельзя удалить раньше срока хранения |
| `DELETE_ON_REQUEST` | Данные, подлежащие прекращению обработки по запросу | Маркетинговые контакты, необязательные анкеты | Найти все копии и удалить/заблокировать обработку |
| `AUDIT` | Журналы доступа и операций | Логи файлового сервера, API, 1С, порталов | Защита от изменения, централизованное хранение |

## Правила присвоения тегов

| Момент | Правило |
|---|---|
| Сбор данных на ресепшене | ФИО, дата рождения, телефон, email получают `PII`; расширенная медицинская анкета получает `PHI`; договор и согласие получают `PII` + `RETENTION_REQUIRED` |
| Приём врача | Медкарта, диагнозы, назначения и заключения получают `PHI` + `CONFIDENTIAL`; запись врача связывается с лечащим врачом и пациентом |
| Анализы | Направление и результат получают `PHI`; внешний обмен получает идентификатор-токен вместо прямых PII |
| Платежи | Платёжные события получают `FIN`; если нужна связь с пациентом, используется токен пациента или номер договора |
| Склад и закупки | Договоры поставщиков, закупки и ТМЦ получают `OPS` + `CONFIDENTIAL`; персональные данные сотрудников в закупках получают `PII` или `HR` |
| Аналитика | Сырые выгрузки получают `RAW` + `ANALYTICS`; обработанные наборы получают `PROCESSED`; наборы для BI/ML/AI должны получить `ANONYMIZED` |
| Секреты и ключи | Ключи шифрования, сертификаты, API-токены и сервисные пароли получают `SECRETS/KEYS` + `CONFIDENTIAL` |
| Удаление и архивирование | Данные маркируются `RETENTION_REQUIRED` или `DELETE_ON_REQUEST` в зависимости от правового основания и срока хранения |

## Связь с RBAC/ABAC

| Роль | Разрешённый доступ | Ограничения |
|---|---|---|
| Пациент | Свои договоры, записи, заключения и результаты анализов | Нет доступа к данным других пациентов |
| Ресепшен | Запись, контакты, договоры, статусы посещений | Нет доступа к диагнозам, полной медкарте и результатам анализов без отдельного основания |
| Врач | PHI своих пациентов и данные приёма | Нет доступа к финансовым данным, кадровым данным и чужим пациентам вне маршрута лечения |
| Кассир | Платёж, чек, сумма, номер договора или токен пациента | Нет доступа к диагнозам, медкартам и расширенным анкетам |
| Бухгалтерия | Финансовые документы, кадровые и налоговые данные | Нет доступа к медицинскому содержанию услуг |
| Склад | ТМЦ, закупки, поставщики, оборудование | Нет доступа к пациентским PII/PHI и зарплатным данным |
| Бизнес-аналитик | Обезличенные и агрегированные датасеты | Нет доступа к сырым PII/PHI, если нет отдельного согласованного основания |
| IT-администратор | Техническое администрирование систем | Доступ к содержимому PII/PHI только как аварийный доступ с обязательным аудитом |
| Технический директор | Архитектурные метаданные, агрегированные риски, аудит | Доступ к содержимому чувствительных данных только при обоснованной необходимости |

ABAC-атрибуты для тонкого контроля:

- филиал;
- лечащий врач;
- роль сотрудника;
- цель обработки;
- статус согласия;
- тег данных;
- состояние данных: `RAW`, `PROCESSED`, `GOLDEN_SOURCE`;
- канал доступа: офисная сеть, VPN, портал, API;
- риск действия: просмотр, изменение, экспорт, массовая выгрузка, удаление.

## Автоматические действия по тегам

| Тег или комбинация | Автоматическое действие |
|---|---|
| `PII` + `CONFIDENTIAL` | Шифрование at rest, запрет публичных ссылок, аудит доступа |
| `PHI` | Доступ только медролям, запрет email-вложений, алерт на массовый экспорт |
| `FIN` | Аудит изменений, сверка с 1С, доступ кассы и бухгалтерии |
| `OPS` + `CONFIDENTIAL` | Доступ складу и бухгалтерии, аудит изменений справочников и закупочных документов |
| `ANALYTICS` + `RAW` | Запрет публикации в BI/ML/AI до обработки, тегирования и проверки риска реидентификации |
| `SECRETS/KEYS` | Хранение в системе управления ключами, ротация, запрет выгрузки в файлы и обязательный аудит выдачи |
| `RAW` + `PHI` | Запрет передачи в BI/ML/AI без обезличивания |
| `ANONYMIZED` | Разрешение аналитического использования после проверки качества обезличивания |
| `DELETE_ON_REQUEST` | Поиск копий в связанных системах и постановка задачи удаления или блокировки обработки |
| `RETENTION_REQUIRED` | Архивирование и запрет удаления до окончания срока хранения |
| `AUDIT` | Запись в неизменяемое хранилище логов и контроль целостности |

## Инструменты

| Инструмент | Роль в модели | Почему подходит |
|---|---|---|
| Apache Atlas | Каталог метаданных, теги, Data Lineage | Open source, подходит как базовый каталог для будущего озера данных |
| Apache NiFi | Управляемые потоки данных и преобразования | Фиксирует маршруты, применяет маскирование/шифрование и даёт мониторинг потоков |
| Active Directory или Keycloak | Идентификация, RBAC/ABAC | Active Directory уже есть в As-Is; Keycloak можно использовать для новых порталов и API |
| Apache Ranger | Политики доступа к данным по тегам | Связывает теги данных с ролями и разрешениями |
| SIEM | Централизованный сбор логов и алерты | Нужен для расследований и обнаружения нетипичных действий |
| DLP | Контроль утечек через почту, файлы и рабочие станции | Закрывает риск пересылки PII/PHI из Excel, PDF и Outlook |
| BigID/Informatica/Collibra | Коммерческие альтернативы discovery и catalog | Подходят при росте масштаба и усложнении ландшафта |

## Процесс внедрения

1. Провести инвентаризацию источников: общий диск, Excel, сканы, 1С, Exchange, `CRM / Patient Profile`, Клиентский портал, Портал ресепшена и API лаборатории.
2. Назначить владельцев данных по доменам: пациентские данные, медицинские данные, финансы, склад, HR, аналитика.
3. Создать каталог тегов и правила присвоения.
4. Просканировать существующие файлы и базы на PII/PHI/FIN/HR.
5. Проставить теги на уровне файла, таблицы, поля и потока данных.
6. Связать теги с ролями и атрибутами доступа.
7. Включить аудит и алерты на действия с `PII`, `PHI`, `FIN` и `HR`.
8. Встроить проверки тегов в релизный процесс новых систем: `CRM / Patient Profile`, Клиентского портала, Портала ресепшена, API лаборатории и `Аналитического слоя с Privacy by Design`.
9. Пересматривать теги и права при изменении процессов, филиалов, ролей или требований хранения.
