# Аудит мер безопасности данных

## Текущее состояние As-Is

| Область | Что есть сейчас | Недостаток | Требуемое улучшение |
|---|---|---|---|
| Идентификация пользователей | Доменная аутентификация через Active Directory | Нет связи прав доступа с категориями данных и бизнес-ролями | RBAC/ABAC, регулярный пересмотр прав, привязка политик к тегам данных |
| Хранение данных | Excel, JPG/PDF, общий диск, файловые базы 1С, Exchange | Нет централизованной классификации, тонкого аудита, шифрования и сроков хранения | Каталог данных, защищённые хранилища, шифрование, аудит, retention-политики |
| Передача данных | Локальная сеть, общий диск, почта, TCP/IP с ККМ, OLE-компонента 1С | Потоки не документированы, защита каналов и состава передаваемых данных не описана | DFD, TLS/VPN для сетевых потоков, DLP для почты, контроль API-контрактов |
| Использование данных | Ручная обработка сотрудниками в Excel/1С/сканах | Сотрудник может видеть больше данных, чем нужно для задачи | Минимальные представления, динамическое маскирование, разделение доменов |
| Аудит | Файлы и системы работают без полноценного аудита действий | Нельзя расследовать просмотр, изменение, выгрузку или удаление чувствительных данных | Централизованные логи, SIEM, алерты на массовые операции и нетипичный доступ |
| Data Lineage | Потоки между IT-продуктами не контролируются | Неясно, откуда данные пришли, как изменились и куда ушли | Data Lineage: источник, преобразование, владелец, дата, получатель, конечное состояние |
| Минимизация | Пациент может заполнять расширенную форму с избыточными сведениями | Лишние данные увеличивают риск утечки и объём защиты | Минимальный набор обязательных полей, отдельные согласия и цели обработки |

## Сопоставление с Privacy by Design

| Принцип | Оценка As-Is | Что нужно сделать |
|---|---|---|
| Проактивность | Реактивная модель: защита не встроена в процессы, риски выявлены уже после накопления данных | До разработки новых систем зафиксировать реестр данных, DFD, роли, теги и контрольные точки |
| Конфиденциальность по умолчанию | По умолчанию данные доступны через общий диск и ручные файлы | Сделать закрытый доступ по умолчанию, открывать данные только по роли и цели обработки |
| Конфиденциальность в дизайне | Excel, сканы и файловые базы не содержат встроенного механизма защиты данных | Встраивать теги, маскирование, аудит и шифрование в Клиентский портал, Портал ресепшена, `CRM / Patient Profile`, API лаборатории и `Аналитический слой с Privacy by Design` |
| Полная функциональность | Сейчас удобство ручной работы достигается за счёт риска утечки | Сохранить рабочие процессы, но перевести их в управляемые формы и защищённые интеграции |
| Комплексная безопасность жизненного цикла | Нет сквозного контроля от сбора до удаления | Описать сбор, хранение, использование, передачу, архивирование и удаление данных |
| Наглядность и прозрачность | Нет прозрачной карты потоков и аудита | Поддерживать DFD, каталог данных, журнал доступа и отчёты по запросам субъектов данных |
| Уважение к приватности пользователя | Пациент не управляет составом данных и согласиями | Ввести согласия, право доступа/исправления/прекращения обработки и понятные уведомления |

## Сопоставление с 152-ФЗ

Компания обрабатывает персональные данные пациентов и сотрудников в РФ. Для As-Is важны базовые требования 152-ФЗ: цель обработки, ограничение доступа, конфиденциальность, сроки хранения и доказуемость законности обработки.

| Требование 152-ФЗ | Проблема As-Is | Что нужно сделать |
|---|---|---|
| Обрабатывать данные под конкретные цели | Расширенные анкеты, Excel и сканы не разделяют обязательные и необязательные данные | Фиксировать цель обработки, минимальный набор полей и отдельные согласия для расширенных данных |
| Ограничивать доступ к персональным данным | Доменная аутентификация не учитывает категорию данных и роль сотрудника | Ввести RBAC/ABAC, теги `PII`/`PHI`/`FIN` и регулярный пересмотр прав |
| Обеспечивать конфиденциальность и защиту от неправомерного доступа | Общий диск, почта и файловые базы 1С хранят PII/PHI без полноценного аудита | Использовать шифрование, DLP, аудит файловых операций, SIEM и защищённые каналы передачи |
| Соблюдать сроки хранения и прекращение обработки | Нет полного реестра копий данных, сроков хранения и механизма удаления по запросу | Завести каталог данных, теги `RETENTION_REQUIRED`/`DELETE_ON_REQUEST` и процедуру поиска всех копий |
| Подтверждать законность обработки | Согласия и договоры лежат в сканах без централизованного статуса | Создать реестр согласий, владельцев данных, журнал изменений и Data Lineage для чувствительных наборов |

## Data Minimization

Минимизация по процессам:

| Процесс | Что минимизировать | Решение |
|---|---|---|
| Запись на приём | Адрес, место работы/учёбы, хронические заболевания не нужны для базовой записи | Разделить обязательные поля записи и расширенную медицинскую анкету |
| Ресепшен и договор | Ресепшену не нужны диагнозы и результаты анализов | Показывать только идентификационные, контактные и договорные данные |
| Касса | Кассиру не нужны медицинские детали услуги сверх данных для оплаты и чека | Передавать код услуги, сумму, номер договора, токен пациента |
| Бухгалтерия | Бухгалтерии не нужны PHI и подробная медкарта | Передавать финансовые документы без диагноза и медицинских заключений |
| Аналитика | BI/ML/AI не должны использовать сырые PII/PHI без необходимости | Использовать агрегированные и обезличенные наборы |
| Лаборатория | Внешней лаборатории не нужен полный профиль пациента | Передавать минимальный набор: токен направления, нужные клинические атрибуты, канал обратной передачи результата |

## Data Lineage

Для каждого чувствительного набора фиксируются:

| Вопрос Data Lineage | Как применить в «Медикаменте» |
|---|---|
| Как данные попадают в систему? | Пациент сообщает данные ресепшену, врачу, через Клиентский портал или API лаборатории |
| Каким обработкам подвергаются? | Ввод в журнал, сканирование, создание договора, запись медкарты, платёж, выгрузка в отчёт |
| Какие системы получают доступ или изменяют? | Excel, общий диск, 1С, Exchange, Jupyter/Python, `CRM / Patient Profile`, Клиентский портал, Портал ресепшена и API лаборатории |
| Где хранятся на каждом этапе? | Рабочая станция, файловый сервер, база 1С, почтовый ящик, архив сканов, аналитическое хранилище |
| Как выходят из системы или достигают конечного состояния? | Чек, отчёт, архив, удаление по сроку хранения, обезличенный датасет, ответ лаборатории |

## Рекомендуемые средства контроля

| Мера | Где применять | Зачем |
|---|---|---|
| RBAC/ABAC | Active Directory, Keycloak, 1С, Клиентский портал, Портал ресепшена, `CRM / Patient Profile` | Ограничить доступ по роли, филиалу, лечащему врачу, цели обработки и тегу данных |
| Шифрование at rest | Файловый сервер, архив сканов, бэкапы, базы данных | Защитить данные при компрометации носителя или сервера |
| TLS/VPN | API лаборатории, `Платёжный шлюз / ККМ`, межсервисные вызовы, удалённый доступ филиалов | Защитить данные в передаче |
| Динамическое маскирование | Интерфейсы ресепшена, кассы, аналитики, поддержки | Показывать только нужные поля и скрывать лишние PII/PHI |
| Статическое маскирование | Тестовые, учебные и аналитические копии | Исключить реальные PII/PHI из непроизводственных сред |
| Токенизация | Пациент, договор, направление в лабораторию, платёжная ссылка | Сократить распространение прямых идентификаторов |
| DLP | Почта, общий диск, рабочие станции | Находить и блокировать несанкционированную передачу PII/PHI |
| SIEM и аудит | Windows Server, 1С, файловые операции, порталы, API | Выявлять массовый экспорт, нетипичный доступ и действия вне роли |
| Каталог данных | Apache Atlas/Collibra/Informatica | Вести теги, Data Lineage, владельцев и политики данных |
| Управляемые потоки | Apache NiFi или аналог | Контролировать передачу между системами, преобразования и мониторинг |

## Приоритеты внедрения

| Приоритет | Действие | Обоснование |
|---|---|---|
| P1 | Инвентаризация PII/PHI и владельцев данных | Без реестра нельзя управлять доступом, удалением и Data Lineage |
| P1 | Разделение доступа к общему диску и включение аудита | Снижает текущий риск массовой утечки |
| P1 | Запрет сырых PHI в аналитике и непроизводственных копиях | Закрывает наиболее опасный сценарий вторичного использования |
| P2 | Каталог тегов и правила RBAC/ABAC | Создаёт основу для `CRM / Patient Profile`, Клиентского портала, Портала ресепшена и API лаборатории |
| P2 | Шифрование архивов, бэкапов и критичных файлов | Защищает данные в состоянии покоя |
| P2 | DLP и SIEM-алерты | Даёт обнаружение утечек и расследуемость |
| P3 | Управляемые интеграционные потоки | Подготовка к масштабированию, API лаборатории и `Аналитическому слою с Privacy by Design` |
