# Оценка узких мест при миграции

## Цель

Выявить потенциальные узкие места при переходе компании «Медикаменте» от ручных файловых процессов и локальных монолитных систем к современной архитектуре с Клиентским порталом, Порталом ресепшена, `CRM / Patient Profile`, `Платёжным шлюзом / ККМ`, API лаборатории и `Аналитическим слоем с Privacy by Design`.

Диаграмма Исикавы: [ishikawa-migration-bottlenecks.drawio](ishikawa-migration-bottlenecks.drawio).

## Контекст миграции

As-Is архитектура держится на локальном Windows Server 2022, Active Directory, файловом сервере, Exchange, Excel, сканах JPG/PDF и двух файловых базах 1С. Данные пациентов, платежи, медицинские карты, результаты анализов и документы передаются вручную через общий диск, почту, Excel и 1С. Аудит действий, управляемые API, единый источник данных, метрики производительности и прослеживаемость потоков отсутствуют или не описаны.

To-Be состояние предполагает рост количества клиентов и сотрудников примерно в пять раз, открытие филиалов, самостоятельную запись через Клиентский портал и мобильное приложение, `CRM / Patient Profile`, `Платёжный шлюз / ККМ`, интеграцию с `Лабораторией`, аналитику BI/ML/AI, аудит доступа и алертинг по нетипичным действиям.

Риск миграции: если перенести ручные и файловые ограничения в новую распределённую архитектуру, узкие места начнут масштабироваться вместе с бизнесом. Последствия — задержки записи, ошибки в медицинских и платёжных данных, простои филиалов, рассинхронизация старого и нового контура, регуляторные риски и перегрузка маленькой IT-команды.

## Ключевые процессы и компоненты

| Область | Компоненты и процессы | Влияние |
|---|---|---|
| Запись и обслуживание пациента | Ресепшен, Excel-журнал, Клиентский портал, Портал ресепшена, уведомления | Это критический путь для роста клиентского потока; ручной ввод и дубли создают задержки и ошибки |
| Медицинская карта | Врач, сканы JPG/PDF, общий диск, `CRM / Patient Profile`, `Медицинский контур` | PHI-данные должны быть доступны быстро, но только нужным ролям; сканы плохо масштабируются и плохо индексируются |
| Анализы | Врач, учёт направлений, `Лаборатория`, API лаборатории | Внешняя интеграция может стать точкой задержек, повторов, расхождений статусов и утечек данных |
| Платежи | Кассир, ККМ, OLE-компонента 1С, `1С:Бухгалтерия`, `Платёжный шлюз / ККМ`, `Платежи / 1С / ККМ` | Финансовый поток требует целостности, идемпотентности и сверки между старым и новым контуром |
| Склад и бухгалтерия | `1С:Торговля и склад`, `1С:Бухгалтерия`, закупки, налоги, зарплата | Файловый режим и интеграция между 1С ограничивают масштабирование и отказоустойчивость |
| Аналитика | Excel, Jupyter/Python, будущее озеро данных, BI/ML/AI | Сырые выгрузки и некачественные данные создают медленные пайплайны и риск некорректных решений |
| Инфраструктура | Windows Server, AD, DNS, DHCP, LDAP, Exchange, локальная сеть, будущий Kubernetes | Один локальный сервер и отсутствие DR/SRE-практик ограничивают рост филиалов и надёжность |

## Диаграмма Исикавы

Диаграмма фиксирует эффект: «снижение производительности и управляемости новой архитектуры после миграции».

Основные категории причин:

- Инфраструктура;
- Данные и хранилища;
- Интеграции;
- ПО и архитектура;
- Процессы;
- Персонал и организация;
- Наблюдаемость, безопасность, соответствие.

## Выявленные узкие места

| Категория | Потенциальная причина | Влияние на миграцию | Приоритет |
|---|---|---|---|
| Инфраструктура | Один локальный Windows Server обслуживает AD, файловый сервер, Exchange и сетевые роли | Единая точка отказа, риск простоя офиса и филиалов при росте нагрузки | P0 |
| Инфраструктура | Файловый режим 1С и общий диск завязаны на локальную сеть | Медленные операции, блокировки файлов, сложное масштабирование филиалов | P0 |
| Инфраструктура | Не определены RTO/RPO, резервирование и аварийное восстановление | Непонятно, сколько данных и времени компания может потерять при сбое | P0 |
| Данные и хранилища | Excel, JPG/PDF и сканы не имеют владельцев, версий и статусов | Сложно мигрировать, очищать, дедуплицировать и проверять данные | P0 |
| Данные и хранилища | Нет золотого источника для пациента, записи, договора, платежа и анализа | Новая система может получить противоречивые данные из нескольких ручных источников | P0 |
| Данные и хранилища | Нет Data Lineage и метаданных преобразований | Нельзя доказать происхождение данных и корректность миграции | P1 |
| Интеграции | Почта, общий диск и Excel используются как интеграционный механизм | Потоки неидемпотентны, не наблюдаемы, плохо восстанавливаются после ошибок | P0 |
| Интеграции | Связка ККМ с 1С через TCP/IP и OLE-компоненту не изолирована API-слоем | `Платёжный шлюз / ККМ` будет зависеть от legacy-интерфейса и ручных сверок | P1 |
| Интеграции | API лаборатории пока без SLA, retry, timeout и безопасных повторов | Ошибки внешнего партнёра могут блокировать медицинский процесс и раскрывать PHI | P1 |
| ПО и архитектура | Домены пациента, записи, медкарты, платежей и аналитики не разделены технически | Изменения в одном процессе будут затрагивать несколько команд и систем | P0 |
| ПО и архитектура | Нет фасада или слоя абстракции над legacy-хранилищами | Нельзя безопасно применять Branch by Abstraction и постепенно заменять компоненты | P1 |
| ПО и архитектура | Нет контрактных, регрессионных и нагрузочных тестов критических сценариев | Производительность новой системы обнаружится только после переключения пользователей | P1 |
| Процессы | Ручной ввод и дублирование между Excel, сканами и 1С | Ошибки миграции будут постоянно появляться во время параллельной эксплуатации | P0 |
| Процессы | Не описаны cutover, rollback, критерии готовности и порядок сверки старой и новой систем | Высокий риск большого переключения без безопасного отката | P0 |
| Процессы | Нет регулярной сверки качества данных и бизнес-метрик | Узкие места будут выявляться по жалобам, а не по метрикам | P1 |
| Персонал и организация | IT-команда состоит из трёх человек, а эксплуатация покрывает всё от принтера до Kubernetes | Перегрузка команды, высокий bus factor, задержки инцидентов и релизов | P0 |
| Персонал и организация | Знания о ручных процессах находятся у отдельных сотрудников | При миграции будут пропущены неформальные потоки данных и исключения | P1 |
| Наблюдаемость, безопасность, соответствие | Нет централизованного аудита действий и мониторинга потоков данных | Нельзя быстро найти причину деградации, утечки или рассинхронизации | P0 |
| Наблюдаемость, безопасность, соответствие | Нет метрик latency, error rate, sync lag, DORA, MTTR, RTO/RPO | Нельзя объективно приоритизировать устранение узких мест | P1 |
| Наблюдаемость, безопасность, соответствие | Доступ не связан с категорией данных и целью обработки | При росте персонала растёт риск блокировок из-за чрезмерной защиты или утечек из-за слабой защиты | P1 |

## Рекомендации и приоритеты

| Приоритет | Мера | Какие узкие места закрывает | Критерий готовности |
|---|---|---|---|
| P0 | Зафиксировать целевые RTO/RPO, схему резервного копирования, восстановления и отказоустойчивости для AD, файлов, 1С и новых сервисов | Единая точка отказа, неуправляемый простой, риск потери данных | Проведён тест восстановления, известны допустимые потери и время восстановления |
| P0 | Провести инвентаризацию и очистку данных до миграции: владельцы, источники, дубли, обязательные поля, статусы, сроки хранения | Противоречивые Excel/сканы/1С, отсутствие золотого источника | Есть реестр наборов данных и правила выбора золотого источника |
| P0 | Выделить доменные границы: пациент, запись, медкарта, лаборатория, платежи, склад, аналитика | Сильная связанность бизнес-логики и данных | Для каждого домена определены владелец, API, хранилище и события |
| P0 | Запретить big-bang переключение критических процессов; использовать поэтапное включение с параллельной сверкой | Риск потери записи, платежей и медицинских данных | Для каждого этапа есть критерии go/no-go и отката |
| P0 | Ввести базовую наблюдаемость: централизованные логи, метрики, алерты, трассировка критических операций | Невидимые задержки и ошибки интеграций | Видны latency, error rate, saturation, sync lag и бизнес-счётчики |
| P1 | Создать API-фасад или адаптер над legacy-источниками для Branch by Abstraction | Прямая зависимость новых сервисов от файловых 1С, Excel и общего диска | Новые компоненты читают и пишут через управляемый интерфейс |
| P1 | Ввести Event Sourcing или управляемый журнал событий между старым и новым контуром | Ручные сверки, рассинхронизация, повторные операции | Есть события, безопасные повторы и контроль отставания |
| P1 | Описать контракты API лаборатории и `Платёжного шлюза / ККМ`: SLA, повторные попытки, тайм-ауты, авторизация, минимальный состав данных | Внешние интеграции как источник задержек и ошибок | Контракты покрыты проверками и мониторингом ошибок |
| P1 | Нагрузочно проверить критические сценарии: запись, просмотр медкарты, создание платежа, получение результата анализа, отчёт | Неизвестная производительность новой архитектуры | Есть исходные показатели As-Is и целевые показатели To-Be |
| P1 | Сформировать кросс-функциональную группу миграции с владельцами доменов, IT, ресепшеном, врачом, кассой, бухгалтерией и аналитиком | Узкие знания у отдельных сотрудников и слабая коммуникация | Для каждого процесса есть владелец решения и согласованный сценарий миграции |
| P2 | Перевести 1С из файлового режима или изолировать её роль до управляемой back-office-интеграции | Блокировки, масштабирование филиалов, сложный аудит | Новые сервисы не зависят напрямую от файловой базы |
| P2 | Ввести каталог данных, Data Lineage и теги чувствительности для мигрируемых наборов | Непрозрачное происхождение данных и риски соответствия | Для каждого набора известны источник, преобразование, владелец и класс данных |

## Метрики для контроля узких мест

Перед миграцией нужно собрать исходные показатели, а затем сравнивать их с целевыми значениями:

| Метрика | Смысл | Где применять |
|---|---|---|
| Время записи пациента | Скорость критического клиентского сценария | Клиентский портал, Портал ресепшена, `CRM / Patient Profile` |
| Время открытия медицинской карты | Производительность доступа врача к PHI | `Медицинский контур` |
| Время получения результата анализа | Задержку внешней лабораторной интеграции | API лаборатории |
| Время фискализации и сверки платежа | Узкие места ККМ, 1С и `Платёжного шлюза / ККМ` | `Платежи / 1С / ККМ` |
| Sync lag между старой и новой системой | Риск рассинхронизации при параллельной работе | Миграционные пайплайны |
| Error rate и retry rate интеграций | Нестабильность внешних и внутренних API | `Лаборатория`, `Платежи / 1С / ККМ`, 1С |
| MTTR | Скорость восстановления после инцидента | Эксплуатация и поддержка |
| RTO/RPO | Допустимый простой и потеря данных | DR-план и резервное копирование |
| Deployment Frequency и Lead Time for Changes | Скорость поставки изменений | Новые сервисы и миграционная команда |
| Change Failure Rate | Качество релизов | Клиентский портал, Портал ресепшена, `CRM / Patient Profile`, API, интеграции |

## Вывод

Узкие места лежат в инфраструктуре, данных, ручных процессах и наблюдаемости. До переноса нагрузки нужно стабилизировать базовый слой: инвентаризировать данные, определить золотой источник, разделить домены, ввести наблюдаемость, описать RTO/RPO и идти через этапы с параллельной сверкой и откатом.
